Pkl's evaluator is a https://www.graalvm.org/latest/graalvm-as-a-platform/language-implementation-framework/[Truffle] interpreter. Initialising it the first time costs a few hundred milliseconds on a JVM and adds roughly 18 MB of JARs to the runtime classpath, most of it `truffle-api`. Once initialised, evaluating further modules takes about a millisecond, so the loader creates a fresh evaluator for every file without a measurable penalty.

For most services the cost is acceptable. Where startup time matters, for example in serverless functions:

* Keep configuration modules small and avoid expensive expressions; evaluation time is dominated by Truffle start-up, not by the module.
* Run on a GraalVM JDK or as a GraalVM native image, where the interpreter starts faster.
* Set `-Dpolyglot.engine.WarnInterpreterOnly=false` if you see Truffle's interpreter warning on other JDKs; the loader sets it when the property is unset.

=== Evaluating Pkl at build time with Micronaut AOT

With https://micronaut-projects.github.io/micronaut-aot/latest/guide/[Micronaut AOT], the `pkl.to.java.config` optimization in `micronaut-pkl-aot` evaluates the configuration modules during the build and generates a class holding their properties, so the optimized application starts without loading Pkl or Truffle. It is off by default. With the Gradle plugin and `io.micronaut.aot` applied:

[source,groovy]
----
micronautPkl {
    convertToJava = true
}
----

With Maven, add `io.micronaut.pkl:micronaut-pkl-aot` to the `aotDependencies` of `micronaut-maven-plugin` and set `pkl.to.java.config.enabled=true` in `aot.properties`.

The optimization converts `application.pkl`, `bootstrap.pkl` and the `application-{env}.pkl` modules of the environments listed in the AOT `possible.environments` or `target.environments` settings. Any other module is still evaluated at startup, so the `.pkl` files stay in the artifact, and so do the `pkl-core` and Truffle JARs.

A module that reads any resource other than a `modulepath:` one, such as an `env:`, `prop:` or `https:` resource, is not converted, because the build machine's values would be frozen into the artifact. Neither is a module containing a `NaN` or infinite `Float`. The build logs a warning and the module is evaluated at startup instead. To convert such a module, replace `read?("env:PORT") ?? 8080` with a Micronaut placeholder such as `"${PORT:8080}"`, which the Environment resolves when the application starts. The `micronaut.config.pkl.*` settings are read from the process that runs the optimizer.

=== GraalVM native image

The loader works in a GraalVM native image. `micronaut-pkl` ships the native-image metadata that Pkl's evaluator needs, so no configuration is required in the application:

* class-initialisation settings that initialise Pkl's generated Truffle node classes at image build time, as Truffle requires, while keeping the rest of `pkl-core` at run time (evaluating Pkl during the image build would capture the build's threads in the image heap);
* resource settings that include the Pkl standard library modules and error-message bundles in the image.

One build-time rule remains: `native-image` refuses to build when the `org.graalvm.polyglot` and `org.graalvm.truffle` artifacts on the classpath are older than the GraalVM performing the build (`Polyglot version compatibility check failed`). `pkl-core` depends on the Truffle release it was built with, so align those artifacts with your GraalVM version, for example in Gradle:

[source,groovy]
----
configurations.configureEach {
    resolutionStrategy.eachDependency { details ->
        if (details.requested.group in ['org.graalvm.truffle', 'org.graalvm.polyglot', 'org.graalvm.sdk']) {
            details.useVersion('25.4.4.1.1') // the version of the GraalVM you build with
        }
    }
}
----

The image uses Truffle's interpreter-only fallback runtime, which is sufficient for evaluating configuration at startup. The repository's `test-suite-graal` module builds such an image and is run by the GraalVM CI workflows.
