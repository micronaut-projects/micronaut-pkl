Micronaut Pkl

Support for the Apple Pkl configuration language in the Micronaut framework

Version: 1.0.0-SNAPSHOT

1 Introduction

Pkl ("Pickle") is Apple’s open-source configuration language. It is typed and object-oriented: modules can amend other modules, values can be derived from one another, properties can declare constraints that are validated when the module is evaluated, and durations and data sizes are first-class values.

Using this module, the Micronaut framework loads configuration from application.pkl files alongside, or instead of, application.yml, application.properties, application.json and application.toml. Pkl’s own evaluator (pkl-core) runs at startup to turn the module into the same flat key/value configuration every other format produces, so @ConfigurationProperties, @Value and ${…​} placeholders work unchanged.

2 Quick Start

To add support for Pkl to an existing project, add the Micronaut Pkl module to your build configuration:

implementation("io.micronaut.pkl:micronaut-pkl")
<dependency>
    <groupId>io.micronaut.pkl</groupId>
    <artifactId>micronaut-pkl</artifactId>
</dependency>

You can then write your application configuration in Pkl:

src/main/resources/application.pkl
micronaut {
  application {
    name = "example"
  }
  server {
    port = 8080
    readTimeout = 30.s
    maxRequestSize = 10.mib
  }
}

datasources {
  ["default"] {
    url = "jdbc:postgresql://\(read?("env:DB_HOST") ?? "localhost"):5432/app"
    maximumPoolSize = 10
  }
}

Property names may be written in camelCase (readTimeout) or, between backticks, in kebab-case ( read-timeout ); both resolve to the same Micronaut property. Nested objects become dotted keys, so the module above defines micronaut.server.port, datasources.default.url and so on.

default is a Pkl keyword that sets the default value of an object’s elements, so datasources { default { …​ } } does not define datasources.default. Write the entry form ["default"] { …​ } as shown above. The loader logs a warning when it finds a default element in a configuration module.

A .pkl file can also be passed through micronaut.config.files or the MICRONAUT_CONFIG_FILES environment variable like any other configuration file. Modules loaded this way are evaluated from their text alone, so they cannot amends or import sibling files.

3 Environment-specific Modules

As with the other formats, application-{env}.pkl is loaded for each active environment and ranks above application.pkl.

Pkl’s way of deriving one module from another is an amends or extends clause. The Micronaut Pkl loader applies one for you: an environment module that declares no module header and no amends or extends clause is evaluated as if it started with a clause pointing at modulepath:/application.pkl, so it can refer to the production values through super and only has to state what differs. The clause is extends when application.pkl is declared open module, which lets the environment module add keys, and amends otherwise, which only lets it override existing ones.

src/main/resources/application-prod.pkl
micronaut {
  server {
    port = 80
  }
}

datasources {
  ["default"] {
    url = "jdbc:postgresql://\(read("env:DB_HOST")):5432/app"
    maximumPoolSize = super.maximumPoolSize * 2
  }
}

If you prefer the merge-by-key behaviour of YAML, where each environment file is independent, start the environment module with a module declaration (for example module prod) or an explicit amends of a different module. The implicit clause is only added when the file has no module header and no amends/extends clause.

The section on production and test configuration describes the recommended layout across src/main/resources and src/test/resources.

The implicit clause is inserted as the first line of the module, so line numbers in Pkl error messages for a derived environment file are offset by one.
Unlike the other configuration formats, duplicate application.pkl resources on the classpath are not detected or merged according to micronaut.config.loading-strategy; the first resource found is evaluated.

4 Production and Test Configuration

A Micronaut application typically keeps its production configuration in src/main/resources and the configuration for tests in src/test/resources. With Pkl the recommended layout is:

src/main/resources/application.pkl        (1)
src/main/resources/application-prod.pkl   (2)
src/test/resources/application-test.pkl   (3)
1 The production module, declared open module application.
2 Optional environment-specific production modules; they derive from the production module automatically.
3 The test module, active for the test environment that @MicronautTest and ApplicationContext.run() enable by default; it derives from the production module automatically.

The production module

Declare the production module open, so that environment and test modules can extend it:

src/main/resources/application.pkl
open module application

micronaut {
  application { name = "orders" }
  server { port = 8080 }
}

datasources {
  ["default"] {
    url = "jdbc:postgresql://db:5432/orders"
    maximumPoolSize = 20
  }
}

With the generated schema (see the previous sections), use extends rather than amends to attach it, because a module that amends another cannot itself be open:

open module application
extends "modulepath:/Micronaut.pkl"

Both forms validate every known property; extends additionally allows the module, and the modules deriving from it, to declare keys the schema does not know.

The test module

A module named application-{env}.pkl that has no module header and no amends/extends clause is loaded with an implicit clause pointing at application.pkl. The loader chooses the clause from the production module:

Production module Implicit clause The environment module may

open module application (recommended)

extends "application.pkl"

Override any value, refer to the production value through super, and add top-level keys that production does not define. Keys inside typed objects (from the schema) remain validated.

No header, or amends "…​" (not open)

amends "application.pkl"

Override values and refer to them through super, and add keys only inside untyped (Dynamic) objects. A new top-level key fails with "Cannot find property".

So a test module usually looks like this:

src/test/resources/application-test.pkl
datasources {
  ["default"] {
    url = "jdbc:h2:mem:orders;DB_CLOSE_DELAY=-1"
    maximumPoolSize = super.maximumPoolSize ~/ 4
  }
}

micronaut {
  server { port = -1 }
}

orders {
  stubPayments = true   // a key only the tests use
}

Because the test module derives from the production module, evaluating it yields the complete merged configuration, which the loader registers as its own property source above the production one. The usual precedence applies: values from application-test.pkl win over application.pkl, @Property and @MicronautTest(propertySources = …​) win over both, and environment variables and system properties win over all files, exactly as with YAML.

Several environments

Every application-{env}.pkl derives from application.pkl, not from the other environment modules. When several environments are active, for example test and integration, Micronaut layers their property sources in environment order, so later environments override earlier ones key by key, as with the other formats.

Replacing instead of deriving

To write an environment module that stands on its own, give it a module header or an explicit amends/extends clause. The loader then leaves it untouched and Micronaut merges it by key with the production module, which is the YAML behaviour:

src/test/resources/application-test.pkl
module test

micronaut { server { port = -1 } }

Such a module can still attach the schema on its own with amends "modulepath:/Micronaut.pkl".

Pitfalls

  • Do not put an application.pkl in src/test/resources to override production: both files share the resource name, the test classpath lists src/test/resources first, and the production module becomes unreachable, so nothing can derive from it. Use application-test.pkl instead.

  • When you write the clause yourself, address the production module through the module path, extends "modulepath:/application.pkl", not with a relative name. Pkl resolves a relative name against the directory or JAR the current module was found in, and src/test/resources and src/main/resources are different classpath entries. The implicit clause already uses the module path form.

  • super refers to the production module’s value at the same path; it is only available in a deriving module, not in a replacing one.

  • A production module that amends the schema cannot be open; switch it to extends if test modules need to add keys.

  • The implicit clause is inserted as the first line of the environment module, so Pkl line numbers in error messages for it are offset by one.

6 Typed Configuration Schema

Pkl’s main advantage over YAML is validation: a module that amends a typed schema is checked for unknown properties, wrong types and out-of-range values when it is evaluated, and the Pkl IDE plugins use the same schema for completion and hover documentation.

Micronaut already ships the information needed for such a schema: every module packages one JSON Schema per @ConfigurationProperties and @EachProperty class under META-INF/micronaut-configuration-schemas/. The micronaut-pkl-generator module turns the schemas found on an application’s classpath into a single Pkl module, so the schema reflects exactly the modules the application depends on, at their exact versions.

runtimeOnly("io.micronaut.pkl:micronaut-pkl-generator")
<dependency>
    <groupId>io.micronaut.pkl</groupId>
    <artifactId>micronaut-pkl-generator</artifactId>
    <scope>runtime</scope>
</dependency>

Generating the module

The Gradle and Maven plugins described in the next section run the generator as part of the build. To run it by hand, use the command line entry point with the application’s runtime classpath:

java -cp micronaut-pkl-generator.jar:... io.micronaut.pkl.generator.PklSchemaGeneratorCli \
    --classpath build/classes/java/main:lib/micronaut-http-server-netty-5.2.2.jar \
    --out src/main/resources/Micronaut.pkl

The same can be done programmatically with SchemaLocator and PklSchemaGenerator. The application’s own @ConfigurationProperties classes are included when the application’s class output is on the classpath, because the Micronaut annotation processor emits schemas for them too.

Using the module

Derive application.pkl from the generated module. extends keeps the production module open, so environment and test modules can add keys (see the production and test configuration section); amends works too but then nothing can extend the production module:

src/main/resources/application.pkl
open module application
extends "modulepath:/Micronaut.pkl"

micronaut {
  application { name = "example" }
  server {
    port = 8080
    netty { serverType = "FULL_CONTENT" }
  }
  executors {
    ["io"] { type = "FIXED"; nThreads = 4 }
  }
}

A misspelled property (prot), a wrong type (port = "8080"), an unknown enum value or a violated constraint fails evaluation with Pkl’s error message naming the file, line and column. The Pkl plugins for IntelliJ, VS Code and Neovim offer completion for the amended module’s properties and show the Javadoc of the Micronaut class on hover.

@Deprecated

Every property is nullable and no defaults are assigned, so amending the schema sets only the values you write; an untouched property produces no configuration key. Property names are camelCase (maxHeaderSize), which Micronaut treats like max-header-size; names that are Pkl keywords are quoted with backticks, for example default .

Limitations

  • Only prefixes that have a schema are known. A typed object rejects unknown properties, so keys for libraries without schemas or that are only read through @Value cannot be placed in an amending module. Declare them in a module that extends the generated one (every generated class and the module are open), or keep them in a second, untyped configuration file.

  • When an @EachProperty prefix such as endpoints also has schemas for named keys (endpoints.health), the prefix becomes a class whose named properties extend the entry type, so endpoints.health.enabled is known while a key without a schema (endpoints.custom) is not.

  • Properties that Micronaut reads as @ReadableBytes are not marked in the schemas yet and are generated as Int; write the byte count.

  • The generated file must be regenerated when dependencies change; commit it or generate it in the build before processResources.

7 Gradle and Maven Plugins

The schema generator is easiest to use through the build plugins, which run it against the application’s runtime classpath (including the application’s own @ConfigurationProperties classes, once compiled) and put the generated module on the classpath so application.pkl can amend it:

src/main/resources/application.pkl
open module application
extends "modulepath:/Micronaut.pkl"

micronaut {
  application { name = "example" }
}

Gradle

Apply the io.micronaut.pkl plugin alongside the Java plugin:

build.gradle
plugins {
    id 'java'
    id 'io.micronaut.pkl' version '{version}'
}

The plugin is published to Maven Central with the other modules, so pluginManagement { repositories { mavenCentral() } } is needed in settings.gradle unless it is also on the Gradle plugin portal.

The plugin adds the generatePklSchema task, which writes build/generated/pkl/Micronaut.pkl and adds that directory to the main resources, so the module is generated before processResources and packaged with the application. The task is cacheable and up to date while the runtime classpath does not change.

The micronautPkl extension configures it:

micronautPkl {
    generateSchema = true                                        // set to false to disable the task
    schemaModuleName = 'Micronaut'                               // the module and file name
    schemaOutputDirectory = layout.projectDirectory.dir('src/main/pkl') // write into the source tree instead
    schemaClasspath.from(configurations.runtimeClasspath)        // defaults to the runtime classpath and the main classes
}

Writing the module into the source tree (and committing it) lets the Pkl IDE plugins resolve amends "Micronaut.pkl" with a relative path. With the default build directory, use the modulepath: form shown above, which the loader resolves on the classpath at run time.

Maven

Bind the generate-pkl-schema goal of micronaut-pkl-maven-plugin:

pom.xml
<plugin>
  <groupId>io.micronaut.pkl</groupId>
  <artifactId>micronaut-pkl-maven-plugin</artifactId>
  <version>{version}</version>
  <executions>
    <execution>
      <goals>
        <goal>generate-pkl-schema</goal>
      </goals>
    </execution>
  </executions>
</plugin>

The goal runs in the process-classes phase, after the project’s own configuration classes have been compiled, and writes Micronaut.pkl into target/classes so that it is packaged. Parameters, each also settable as a system property:

Parameter Property Default

outputDirectory

micronaut.pkl.outputDirectory

${project.build.outputDirectory}

moduleName

micronaut.pkl.moduleName

Micronaut

skip

micronaut.pkl.skip

false

Without a build plugin, the generator can also be run directly; see the previous section.

8 Sandboxing and Settings

A Pkl module is a program. Following the Pkl threat model, the loader decides what a configuration module may import and read; the module itself cannot widen these permissions.

By default a module may:

  • import modules from the Pkl standard library (pkl:) and from the classpath (modulepath:), so amends "modulepath:/AppConfig.pkl" works;

  • read env: environment variables, prop: system properties and modulepath: classpath resources;

  • when the module itself was loaded from the file system (for example from the working directory), import and read file: modules and resources below the module’s own directory.

Network access (https:), Pkl packages (package:) and arbitrary file access are disabled. They can be allowed with the following system properties, or the equivalent environment variables (MICRONAUT_CONFIG_PKL_ALLOWED_MODULES, and so on). These are read from system properties and environment variables only, because the loader runs before the Environment exists.

Setting Description Default

micronaut.config.pkl.enabled

Set to false to disable the loader.

true

micronaut.config.pkl.timeout

Maximum evaluation time per module, for example 500ms, 30s or 2m. Pkl is Turing complete and does not bound CPU or memory, so the timeout is the only guard against a runaway module.

10s

micronaut.config.pkl.allowed-modules

Comma-separated regular expressions matched against the start of module URIs, added to the defaults. For example https:,package:.

micronaut.config.pkl.allowed-resources

Comma-separated regular expressions matched against the start of resource URIs, added to the defaults. For example https:.

Evaluation errors, including security violations and timeouts, abort startup with a ConfigurationException that carries Pkl’s own message, which names the module, line and column.

To customise the evaluator further, for example to register a Pkl ResourceReader for a secrets store, subclass PklPropertySourceLoader, override createEvaluator, and register the subclass instead of the default in META-INF/services/io.micronaut.context.env.PropertySourceLoader.

9 Startup Cost

Pkl’s evaluator is a Truffle interpreter. Initialising it the first time costs a few hundred milliseconds on a JVM and adds roughly 18 MB of JARs to the runtime classpath, most of it truffle-api. Once initialised, evaluating further modules takes about a millisecond, so the loader creates a fresh evaluator for every file without a measurable penalty.

For most services the cost is acceptable. Where startup time matters, for example in serverless functions:

  • Keep configuration modules small and avoid expensive expressions; evaluation time is dominated by Truffle start-up, not by the module.

  • Run on a GraalVM JDK or as a GraalVM native image, where the interpreter starts faster.

  • Set -Dpolyglot.engine.WarnInterpreterOnly=false if you see Truffle’s interpreter warning on other JDKs; the loader sets it when the property is unset.

A build-time optimisation for Micronaut AOT that evaluates .pkl modules during the build and replaces them with a static property source, removing the evaluator from the deployed artifact, is planned.

GraalVM native image

The loader works in a GraalVM native image. micronaut-pkl ships the native-image metadata that Pkl’s evaluator needs, so no configuration is required in the application:

  • class-initialisation settings that initialise Pkl’s generated Truffle node classes at image build time, as Truffle requires, while keeping the rest of pkl-core at run time (evaluating Pkl during the image build would capture the build’s threads in the image heap);

  • resource settings that include the Pkl standard library modules and error-message bundles in the image.

One build-time rule remains: native-image refuses to build when the org.graalvm.polyglot and org.graalvm.truffle artifacts on the classpath are older than the GraalVM performing the build (Polyglot version compatibility check failed). pkl-core depends on the Truffle release it was built with, so align those artifacts with your GraalVM version, for example in Gradle:

configurations.configureEach {
    resolutionStrategy.eachDependency { details ->
        if (details.requested.group in ['org.graalvm.truffle', 'org.graalvm.polyglot', 'org.graalvm.sdk']) {
            details.useVersion('25.4.4.1.1') // the version of the GraalVM you build with
        }
    }
}

The image uses Truffle’s interpreter-only fallback runtime, which is sufficient for evaluating configuration at startup. The repository’s test-suite-graal module builds such an image and is run by the GraalVM CI workflows.
